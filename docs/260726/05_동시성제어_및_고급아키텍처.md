# 05. 동시성 제어 및 고급 아키텍처

웹 콘솔 도입으로 "같은 사장이 모바일+웹을 동시에 쓰는" 시나리오와 "같은 매장을 사장+매니저가 각자 다른 기기에서 동시 편집하는" 시나리오가 새로 생긴다. 이 문서는 그로 인한 동시성 문제와 대응 설계를 정의한다.

## 1. 문제 유형 분류

| 유형 | 예시 | 위험도 |
|---|---|---|
| 동시 편집(Lost Update) | 사장이 웹에서 시프트A를 수정하는 동안 매니저가 모바일에서 같은 시프트A를 수정 | 높음 — 데이터 유실 |
| 중복 실행(Double Submit) | 급여 확정 버튼을 웹에서 더블클릭하거나, 네트워크 재시도로 같은 정산 요청이 2번 전송 | 높음 — 금전적 이중 계산 |
| 세션 경쟁(Session Race) | 웹 여러 탭에서 로그아웃/재로그인이 겹침 | 낮음 |
| 캐시 불일치 | 웹 BFF 캐시와 백엔드 Ehcache가 다른 시점의 데이터를 보여줌 | 중간 |
| WebSocket 재연결 중 이벤트 유실 | 브라우저 절전/네트워크 전환으로 STOMP 재연결 시 그 사이 이벤트를 놓침 | 중간 |

## 2. 동시 편집 — 낙관적 락(Optimistic Locking)

**범위 확정(2026-07-26, 2차 확인): 낙관적 락이 필요한 엔티티 전부에 적용한다.** "전부"의 기준은 다음과 같이 정의한다 — *사용자(사장/매니저/직원)가 값을 수정(UPDATE)할 수 있는 모든 도메인 엔티티*에 `@Version`을 적용하고, *한 번 기록되면 수정되지 않는 append-only 로그·감사·토큰성 엔티티*는 대상에서 제외한다(제외 사유: 애초에 UPDATE 경합이 발생하지 않아 `@Version`이 무의미).

### 2.1 이미 적용됨 (5종, 기존 코드 확인 완료)

`Store`, `EmployeeStoreRelation`, `EmploymentAmendment`, `ElectronicSignatureEnvelope`, `ElectronicSignatureParty` — 이미 `@Version` 필드 보유.

### 2.2 신규 적용 대상 (마이그레이션 필요, 전체 목록은 [06_DB_마이그레이션계획.md](06_DB_마이그레이션계획.md) §2.1 참고)

출퇴근(Attendance/AttendanceApprovalRequest/AttendanceCorrectionRequest/AttendanceIrregularity/BreakRecord), 스케줄(WorkShift/ShiftTemplate/ShiftTemplateEntry/ShiftSwapRequest/ShiftSwapApplicant/TimeOff), 급여(Payroll/PayrollDetail/PayrollPolicy/PayrollBonus/PayslipFreeGrant), 직원·계약(EmployeeProfile/EmployeeDocument/LaborContract/LaborInfo/MasterProfile/MasterStoreRelation/User), 매장(StoreNfcTag/StoreNotice/BusinessEntity/PolicyInfo/TaxInfo/TipInfo), 구독·결제(Subscription/Purchase/PurchaseItem), 구인채용(JobPosting/JobOffer/JobApplication/JobSeekingProfile), 기타(CustomerInquiry/QnaInfo/TaxServiceOrder) — 총 34개 엔티티.

### 2.3 제외 (append-only 로그·감사·토큰, @Version 무의미)

`AttendanceNotice`, `DomainEvent`, `ElectronicSignatureAccessAudit`, `ElectronicSignatureAttempt`, `ElectronicSignatureOutbox`, `EmploymentTypeChangeLog`, `NoticeRead`, `NotificationInbox`, `PasswordResetToken`, `PaymentHistory`, `ReminderLog`, `RetentionPurgeSchedule`, `StoreDelegationAudit`(단 §4.4/[04_보안정책.md](04_보안정책.md) §8의 `accessChannel` 컬럼 추가 대상이긴 함 — 락과는 무관), `TaxReportSendLog`, `WageHistory`, `RefreshToken`, `DeviceToken`, `StorePhoto`(전체 교체/삭제만 있고 부분 UPDATE 없음), `TermsAgreement`(버전별 append-only 동의 기록).

### 2.4 동작 원칙

- 클라이언트는 조회 시 받은 `version`을 수정 요청에 그대로 담아 보내고, 백엔드는 `OptimisticLockException` 발생 시 **409 Conflict**로 응답한다(`.claude/rules/api-design.md`에 409를 정식 추가 완료).
- FE(웹)는 409 수신 시 "다른 곳에서 먼저 수정됨 — 최신값을 다시 불러오시겠습니까?" UX로 처리한다. 자동 병합(merge)은 하지 않는다 — 급여·근로조건 데이터는 침묵 병합이 노무 리스크로 이어질 수 있으므로 항상 사용자에게 명시적으로 알린다.
- 비관적 락(`SELECT FOR UPDATE`)은 급여 계산처럼 **짧고 확실하게 끝나는 트랜잭션**에 한해 §7에서 별도로 다룬다 — 낙관적 락과 혼용하지 않고 영역을 분리한다.
- 34개 엔티티 전체에 동시 적용하는 것은 리스크가 크므로(회귀 테스트 범위 확대), [08_개발로드맵.md](08_개발로드맵.md)의 Phase별로 해당 Phase가 다루는 엔티티부터 순차 적용한다 — 예: Phase 2(스케줄) 착수 시 WorkShift·TimeOff·ShiftSwap 계열부터.

## 3. 중복 실행 방지 — 멱등성 키(Idempotency Key)

- 급여 확정, 계약 발송, 결제/구독 변경 등 **금전·법적 효력이 있는 POST 요청**에는 클라이언트가 생성한 `Idempotency-Key` 헤더를 요구한다.
- 백엔드는 `(idempotencyKey, storeId)`를 Redis에 짧은 TTL(예: 10분)로 기록해두고, 동일 키의 재요청은 처음 처리 결과를 그대로 반환한다(재계산하지 않음).
- 이는 기존 결제 멱등 처리(수익화 코드, 메모리 `monetization-code` 참고)와 동일한 패턴을 급여·계약 도메인으로 확장하는 것이다 — 새 개념 도입이 아니라 기존에 검증된 패턴의 재적용.
- 프론트엔드(웹)는 버튼 클릭 시 즉시 비활성화(debounce)하는 것과 별개로, 네트워크 재시도가 발생해도 서버가 최종 방어선이 되도록 헤더를 반드시 포함한다.

## 4. 세션 동시성

- 다중 탭은 허용하되, 세션 자체는 서버(Redis)에 단일 소스로 존재하므로 탭 간 경쟁 문제가 없다(각 탭이 같은 쿠키를 공유).
- "다른 기기 모두 로그아웃"(세션 일괄 revoke, [04_보안정책.md](04_보안정책.md) §1)은 Redis에서 해당 사용자의 세션 키 전체를 삭제하는 방식으로 구현하며, 이는 원자적 연산(`SCAN`+`DEL` 또는 세션 키에 사용자ID 인덱스를 별도로 유지)으로 처리한다.
- **세션 저장소 Redis는 초기 출시 시점부터 Sentinel(또는 Cluster) 이중화를 적용**한다(단일 인스턴스로 시작 후 나중에 이중화하는 단계적 접근을 택하지 않음) — 세션 Redis 장애는 곧 전체 사장의 웹 로그인 불가로 직결되는 단일장애점(SPOF)이라 리스크가 크다고 판단([01_시스템아키텍처.md](01_시스템아키텍처.md) §5, [06_DB_마이그레이션계획.md](06_DB_마이그레이션계획.md) §4, [07_배포_운영계획.md](07_배포_운영계획.md) §1 Phase 0 인프라 항목에 반영).

## 5. 캐시 정합성

- 백엔드 Hibernate 2차 캐시(Ehcache)는 `@Cacheable`/`@CacheEvict`가 **프록시 진입점(public 메서드)**에서만 동작하는 기존 제약을 그대로 따른다(CLAUDE.md 핵심 규칙) — 신규 `/api/web/**` 서비스 메서드를 작성할 때도 자기호출(this.method()) 금지 원칙을 재확인한다.
- 웹 BFF(Next.js) 레이어에 추가 캐시를 둘 경우(예: 대시보드 집계 응답을 수 초간 캐시), **쓰기 API 성공 응답 직후 해당 BFF 캐시를 명시적으로 무효화**하는 로직을 함께 구현한다 — 그렇지 않으면 "저장했는데 화면에 안 보인다"는 기존에 이미 한 번 겪은 버그 패턴(메모리 `list-stale-after-write-focus` 참고)이 웹에서 재현된다.
- 원칙: **BFF 캐시는 짧게(수 초~수십 초), 쓰기 시 적극적으로 무효화**. 장기 캐시가 필요한 데이터는 BFF가 아니라 백엔드 Ehcache/Redis에 둔다.

## 6. WebSocket 재연결과 이벤트 유실 방지

- 브라우저 탭이 백그라운드로 전환되거나 절전모드에 들어가면 STOMP 연결이 끊길 수 있다. 재연결 시:
  1. 재연결 성공 즉시 **현재 화면에 필요한 핵심 데이터를 REST로 재조회**(reconciliation fetch)해 끊긴 동안의 이벤트 유실을 보정한다.
  2. WebSocket 이벤트만을 유일한 데이터 소스로 신뢰하지 않는다 — 항상 "이벤트는 갱신 신호일 뿐, 진실은 REST 재조회"라는 기존 FE 원칙(`frontend.md`의 "파생 상태는 서버 원본 필드로 계산" 규칙)을 웹에도 동일 적용한다.
- 재연결 백오프는 지수적으로(1s→2s→4s...최대 30s) 적용해 서버 부하를 방지한다.

## 7. 급여 계산 동시 요청 차단

- 동일 매장·동일 정산주기에 대한 급여 계산 요청이 웹/모바일에서 동시에 들어올 경우를 대비해, `PayrollController.calculate` 진입점에서 **Redis 분산 락**(`(storeId, payrollCycleId)` 키)을 획득한 뒤에만 계산을 수행하고, 락 획득 실패 시 409를 반환한다.
- **분산 락 구현 방식 확정: 자체 구현**(Redisson 등 외부 라이브러리 도입 안 함). `SET key value NX PX {ttl}`로 원자적 획득, 해제는 Lua 스크립트로 "내가 획득한 락인지(value가 내가 넣은 토큰과 일치하는지) 확인 후 삭제"를 원자적으로 수행해 락 소유자가 아닌 요청이 실수로 남의 락을 해제하는 것을 방지한다. 자체 구현을 택한 이유: 이 프로젝트의 분산 락 사용처가 급여 계산 1곳으로 한정적이라 Redisson 전체 기능(재진입 락, 공정 락, pub/sub 기반 대기 등)이 과설계이고, 이미 보유한 `spring-boot-starter-data-redis`의 `RedisTemplate`만으로 충분하다.
- 이는 §3의 멱등성 키와는 별개 방어선이다 — 멱등성 키는 "같은 요청의 중복"을, 분산 락은 "다른 요청(다른 idempotency key)이지만 같은 대상에 대한 동시 계산"을 막는다.

## 8. 트랜잭션·알림 원칙 계승

- 웹 전용 신규 컨트롤러/서비스도 기존 원칙을 그대로 따른다: 쓰기 서비스 `@Transactional`, 조회 `@Transactional(readOnly = true)`, WebSocket/FCM 알림 발행은 반드시 `afterCommit`에서.

## 9. 확정 (2026-07-26, 2차 확인)

- 낙관적 락 적용 범위: append-only 로그·감사·토큰을 제외한 쓰기 가능 엔티티 전부(34종, §2.2) — Phase별 순차 적용
- Redis 분산 락: 자체 구현(`SET NX PX` + Lua 원자적 해제) 확정
- 409 Conflict를 [api-design.md](../../.claude/rules/api-design.md) 상태코드 표에 정식 추가 완료

남은 확인 필요 항목 없음.
