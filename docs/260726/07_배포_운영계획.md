# 07. 배포 및 운영 계획

## 1. 배포 환경 (확정)

| 옵션 | 설명 | 장단점 |
|---|---|---|
| **A. 기존 서버에 컨테이너 추가 (채택)** | 현재 `docker-compose.yml`이 도는 서버에 Next.js 컨테이너 추가 | 초기비용 최소, 저장소 구조 결정([01_시스템아키텍처.md](01_시스템아키텍처.md) §5 모노레포 `web-master/`)과 배포 파이프라인이 자연스럽게 일치. 단 트래픽 급증 시 백엔드와 리소스 경합 — 이 경우 B안으로 프론트만 분리 이전 |
| B. 별도 클라우드(Vercel 등 Next.js 특화 PaaS) | 프론트만 Vercel/유사 서비스, 백엔드는 기존 서버 유지 | Next.js 배포 최적화(엣지 캐싱, 프리뷰 배포) 자동 획득, 단 백엔드와 리전/네트워크 분리로 지연 발생 가능. 트래픽 증가 시 전환 대상 |
| C. 클라우드 전체 이전(AWS 등) | 백엔드까지 포함해 클라우드로 이전 | 확장성 최선, 단 이번 프로젝트 범위를 초과하는 대규모 작업 — 채택 안 함 |

**확정**: **A안**으로 시작한다. 근거: 모노레포·docker-compose 통합 결정([01_시스템아키텍처.md](01_시스템아키텍처.md))과 가장 일관되고, 별도 클라우드 계약·네트워크 설정 없이 즉시 착수 가능. 트래픽이 실제로 백엔드와 경합할 정도로 커지면 그때 B안으로 프론트만 분리하는 마이그레이션 경로를 열어둔다(지금 미리 B안 인프라를 구축하지 않음 — 과설계 방지).

## 2. 로컬 개발 환경

```yaml
# docker-compose.yml 추가 예시 (검토용)
services:
  sodam-web-master:
    build: ./web-master
    ports:
      - "3000:3000"
    environment:
      - BACKEND_INTERNAL_URL=http://sodam-be:7070
    depends_on:
      - sodam-be
```

- 백엔드는 기존과 동일하게 `docker compose up -d`로 기동. 이번에 `docker-compose.yml`에 `sodam-web-master` 서비스를 통합하기로 확정했으므로([01_시스템아키텍처.md](01_시스템아키텍처.md) §5) 풀스택을 한 번에 띄우는 것이 기본 경로이며, 개별 개발자가 웹 프론트만 빠르게 반복 작업할 때는 `npm run dev` 단독 구동도 계속 지원한다(Hot Reload 속도 우선). CI/스테이징은 항상 컨테이너 빌드로 검증한다.

## 3. CI/CD

- 웹 프로젝트는 신규 리포지토리 또는 모노레포 내 신규 디렉터리(`web-master/`)로 시작 — 위치 결정은 §6 확인 필요.
- CI 파이프라인: lint → typecheck → unit test(Vitest) → build → (스테이징 배포 시) E2E(Playwright).
- 기존 모바일/백엔드 CI와 트리거를 분리한다(웹 코드 변경이 백엔드 빌드를 유발하지 않도록, 반대도 마찬가지) — 모노레포라면 path filter로 분리.
- 배포 전 게이트: `npm audit`(고위험 취약점 발견 시 배포 차단), Lighthouse 성능 점수 임계치(예: 90점 미만 시 경고).

## 4. 모니터링 및 에러 추적

- 기존 Sentry 연동을 웹 프로젝트에도 확장(`SODAM_INTEGRATION_SENTRY_MODE` 패턴과 유사하게 웹 전용 DSN 발급).
- 헬스체크: Next.js `/api/health` 엔드포인트 신설, 백엔드 기존 `actuator/health`와 별개로 모니터링 대상에 추가.
- 핵심 모니터링 지표: 웹 세션 로그인 성공률, BFF 응답 지연(P95), WebSocket 재연결 빈도, 급여 계산 API 에러율.

## 7. 테스트 전략

- 단위: Vitest, 백엔드 신규 `/api/web/**`는 기존 `application-test.yml` 프로필로 JUnit 5 테스트.
- 통합: Playwright E2E로 로그인→대시보드→핵심 워크플로우(스케줄 편성, 급여 정산) 스모크 테스트.
- 회귀 방지: 웹 신규 API가 기존 모바일 API 계약을 깨지 않았는지 확인하는 계약 테스트(선택적 도입 검토).
