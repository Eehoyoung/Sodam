# 04. 보안 정책

기존 [.claude/rules/security.md](../../.claude/rules/security.md) 원칙을 웹 콘솔에도 전부 계승하며, 웹 특유의 위협(세션 하이재킹, CSRF, XSS 표면 확대)에 대한 추가 정책을 정의한다.

## 1. 인증

- 세션은 Redis에 저장하고, 클라이언트에는 `HttpOnly` + `Secure` + `SameSite=Strict` 쿠키(`sodam_web_sid`)로만 전달한다. JS에서 세션 식별자를 읽을 수 있는 경로를 만들지 않는다.
- 세션 TTL: 기본 30분 유휴 만료 + 12시간 절대 만료(둘 중 먼저 도달하는 조건 적용). 모바일 JWT(액세스 1시간/리프레시 7일)보다 짧게 잡는 이유는 공용 PC·매장 카운터 PC에서 사용될 가능성을 고려한 것.
- 세션 만료 시 반드시 **401**을 반환한다(403 금지) — 기존 JWT 갱신 규칙과 동일한 이유(FE가 401만 보고 재인증 플로우로 분기).
- **고위험 작업 step-up 재인증**: 급여 확정(`PAYROLL_CONFIRM` 계열), 매니저 권한 부여, 직원 비활성화, 계약 발송 등 기존 모바일에서도 재인증을 요구하는 작업은 웹에서도 동일하게 비밀번호 재확인 또는 세션 재검증을 요구한다(PRD §4.6/§4.11 원칙 계승).
- 다중기기/다중탭 로그인은 허용하되, 설정 화면에서 "다른 기기 모두 로그아웃"(세션 일괄 revoke)을 제공한다.

## 2. CSRF 방지

쿠키 기반 세션은 CSRF에 취약하므로 다음을 모두 적용한다(방어 심층화):

1. `SameSite=Strict` 쿠키 속성 (1차 방어)
2. **Double Submit Cookie 패턴을 자체 구현으로 확정**(Spring Security 기본 CSRF 토큰 저장소는 사용하지 않음): 로그인 시 CSRF 토큰을 별도의 non-HttpOnly 쿠키로 발급하고, 상태변경 요청(POST/PUT/DELETE)마다 커스텀 헤더(`X-Sodam-CSRF`)로 동일 값을 전송해 서버가 대조. 자체 구현을 택한 이유: 세션 인증 자체도 Spring Session Data Redis 기반 커스텀 필터체인이라, CSRF 토큰도 같은 필터 체인 안에서 세션과 함께 발급·검증하는 편이 배선이 단순함
3. `Origin`/`Referer` 헤더 검증을 백엔드 `/api/web/**` 필터에서 수행

## 3. XSS/콘텐츠 보안

- Next.js 기본 이스케이프(React JSX)를 신뢰하되, `dangerouslySetInnerHTML` 사용을 금지 목록에 올린다(코드리뷰 체크리스트).
- `Content-Security-Policy` 헤더 적용: `default-src 'self'`, 외부 스크립트는 화이트리스트(카카오/토스 SDK 등 명시적 허용)만.
- `X-Frame-Options: DENY` 또는 `frame-ancestors 'none'`로 클릭재킹 방지 — 급여·계약 등 금융/법적 액션 화면이 iframe에 삽입되는 것을 원천 차단.
- 파일 업로드(매장 사진, 서류)는 기존 백엔드 검증(확장자·크기·경로조작 차단)을 그대로 통과해야 하며, 웹 업로드 폼에서도 클라이언트측 사전 검증을 추가하되 신뢰 경계로 사용하지 않는다.

## 4. Rate Limiting / 브루트포스 방지

- 로그인(`/api/web/auth/login`)에 별도 Bucket4j 정책 적용: IP당 분당 5회, 계정당 분당 10회 초과 시 429 + 지수백오프 안내.
- **계정 임시 잠금 정책 확정**: 동일 계정에 대해 **연속 로그인 실패 5회**(성공 시 카운터 리셋) 시 15분간 해당 계정 로그인을 잠근다. 이는 §4의 IP 기준 rate limit과는 별개 방어선이다 — rate limit은 짧은 시간 내 시도 횟수를, 계정 잠금은 시간창과 무관하게 누적 실패 자체를 본다.
- 기존 엔드포인트의 Rate limit 설정은 웹 트래픽 유입을 이유로 완화하지 않는다(security.md 원칙).

## 5. 인가

- `StoreAccessGuard` 기반 매장 단위 BOLA 방지 원칙을 신규 `/api/web/**` 컨트롤러에도 동일 적용하며, **가드 호출은 try 블록 밖에 위치**시킨다(CLAUDE.md 패턴 준수).
- 세션 인증 경로에서 구성되는 `Authentication`도 기존 JWT 경로와 동일한 principal 구조를 가져야 `StoreAccessGuard`·`@EmployeeOrMaster`·`assertMasterOrManagerPermission` 등 기존 인가 로직을 변경 없이 재사용할 수 있다([01_시스템아키텍처.md](01_시스템아키텍처.md) §4.2).
- 역할 구분 테스트(사장 전용 API에 직원/매니저 세션으로 접근 시 403) 를 신규 웹 전용 엔드포인트 각각에 대해 추가한다.

## 6. PII 보호

- PII 암호화(AES-256-GCM, `SODAM_SECURITY_PII_ENCRYPTION_KEY`) 컬럼 정책은 웹 경로로 조회되는 데이터에도 동일 적용(이미 백엔드 레벨이므로 자동 적용되나, DTO 필드 선별 원칙을 신규 BFF 응답에도 재확인).
- 웹 로그(Next.js 서버 로그, 프록시 로그)에 PII 원문·GPS 좌표를 남기지 않는다 — 마스킹 유틸을 BFF 레이어에도 이식.
- 브라우저 개발자도구 네트워크 탭에 노출되는 응답이라도 불필요한 PII 필드는 포함하지 않는다(엔티티 직접 반환 금지 원칙 계승).

## 7. 시크릿 관리

- 웹 프로젝트의 `.env`(Next.js `NEXT_PUBLIC_*` 제외 서버 전용 시크릿)는 절대 `NEXT_PUBLIC_` 접두사를 붙이지 않는다 — 접두사가 붙으면 클라이언트 번들에 노출되므로, 세션 암호화 키·백엔드 내부 통신 시크릿 등은 서버 전용 env로만 관리.
- `application-prod.yml`과 동일하게 웹 프로젝트도 example 파일만 커밋, 실제 값은 커밋 금지.

## 8. 감사 로그

- 매니저 대리 작업, 급여 확정 행위자 기록 등 기존 감사 로그 원칙(PRD §4.11)을 웹에서 수행된 작업에도 동일하게 기록한다 — **`accessChannel`(`WEB`/`MOBILE`) 메타데이터 컬럼 추가를 확정**한다. 대상 테이블은 `store_delegation_audit`(매니저 위임 감사이력) — 상세 마이그레이션은 [06_DB_마이그레이션계획.md](06_DB_마이그레이션계획.md) §2.2.

| A02 암호화 실패 | PII AES-256-GCM 계승, 쿠키 Secure 플래그, TLS 강제 |
| A03 인젝션 | JPA 파라미터 바인딩 원칙 계승, 네이티브 쿼리 조립 금지 |
| A04 안전하지 않은 설계 | 세션/JWT 이원화를 명시적으로 설계해 인가 로직 분기 최소화 |
| A05 보안 설정 오류 | CSP/X-Frame-Options/HSTS 헤더 명시 적용 |
| A06 취약한 컴포넌트 | Next.js/의존성 정기 업데이트, `npm audit` CI 게이트 |

| A08 SW/데이터 무결성 실패 | CI에서 lockfile 검증, 서명된 배포 아티팩트 |
| A09 로깅/모니터링 부족 | 감사로그 확장, Sentry 웹 프로젝트 연동([07_배포_운영계획.md](07_배포_운영계획.md)) |
