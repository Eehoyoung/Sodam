# 01. 시스템 아키텍처

## 1. 기존 자산 검토 — `react-native-web`을 기반으로 하지 않는 이유

조사 결과 `frontend/package.json`에 `react-native-web`과 `build:web*` 스크립트가 이미 존재한다. 이 자산을 사장 웹 콘솔의 기반으로 삼을지 검토했다.

| 항목 | RN Web 재사용 | 신규 Next.js 프로젝트 |
|---|---|---|
| 목적 부합성 | 모바일 화면을 그대로 웹에 렌더링하는 데 최적화 — 이번 목표(데스크톱 대시보드, 넓은 레이아웃, 데이터 밀도 높은 테이블/보드)와 어긋남 | 데스크톱 SaaS 대시보드 패턴(사이드바+멀티패널)에 처음부터 적합 |
| SEO/SSR | RN Web은 SSR 미지원(CSR 전용) — 로그인 랜딩 등에서 불리 | Next.js App Router로 SSR/스트리밍 가능 |
| AI 기능 확장성 | RN 컴포넌트 생태계는 AI 코드생성 도구 학습 데이터가 상대적으로 적고, 서버 사이드 AI 호출(스트리밍 응답 등)을 붙이기 번거로움 | Vercel AI SDK 등 Next.js 생태계가 LLM 스트리밍 UI 패턴을 표준으로 제공 — 요구사항의 "AI 기능 추가 시 유지보수 용이" 조건에 부합 |
| 개발 인력 재사용 | RN 개발자가 그대로 작업 가능 | React 지식은 공유되나 Next.js 학습 필요(단, React 19 문법은 동일) |
| 결론 | 모바일 화면 공유가 목적이면 유리하나, 이번 프로젝트 목적과 불일치 | **채택** |

**결정**: 사장 웹 콘솔은 `frontend/` RN Web 빌드와 무관한 **신규 프로젝트**(가칭 `web-master/` 또는 별도 리포지토리)로 시작한다. 기존 RN Web 파이프라인은 유지·건드리지 않는다.

## 2. 프론트엔드 기술스택 (자율 선정)

사용자가 "SaaS에 편리하고 보편적으로 쓰이며, AI 기능 추가 시 유지보수성이 좋은 스택"을 조건으로 자율 선정을 위임했다. 아래와 같이 확정한다.

| 영역 | 선정 | 근거 |
|---|---|---|
| 프레임워크 | **Next.js 15 (App Router) + TypeScript** | 현재 SaaS 대시보드 업계 표준. Server Components로 초기 로딩 최적화, Route Handlers를 BFF로 활용 가능 |
| 서버 상태 | **TanStack Query** | 기존 모바일 앱(`frontend`)과 동일 — 팀 학습곡선 최소화, 캐시/무효화 패턴 공유 |
| 클라이언트 상태 | **Zustand** | Redux 대비 보일러플레이트 적음, 대시보드 UI 상태(사이드바, 필터, 모달) 관리에 충분 |
| 스타일링/컴포넌트 | **Tailwind CSS + shadcn/ui** | SaaS 대시보드 구축 속도가 가장 빠른 조합 중 하나, 컴포넌트를 코드로 소유하므로 커스터마이징 자유롭고 AI 코드생성 도구와 궁합이 좋음(널리 학습된 패턴) |
| 실시간 | **@stomp/stompjs** | 모바일 앱과 동일 라이브러리 — STOMP 프로토콜 공유, 팀 지식 재사용 |
| 폼 검증 | **React Hook Form + Zod** | 백엔드 Bean Validation과 유사한 스키마 선언 방식, 타입 안전성 |
| 날짜 | **date-fns** | 기존 FE 규칙(`frontend.md`)과 동일 — Asia/Seoul 명시적 처리 원칙 계승 |
| 테스트 | **Vitest + Testing Library + Playwright(E2E)** | frontend에 이미 Vitest/Playwright 흔적 존재(`build:web` 파이프라인), 도구 일관성 |
| 배포 런타임 | **Node.js 20 LTS** | Next.js 표준 런타임 |

이 스택은 신규 도입이므로 [08_개발로드맵.md](08_개발로드맵.md) Phase 0에서 프로젝트 스캐폴드·린트·CI 배선을 별도 작업으로 잡는다.

## 3. 백엔드 연동 전략 — 하이브리드(재사용 + 웹 전용 BFF)

사용자 결정: "공통은 재사용하되 웹앱 충돌 억제와 웹 UX 최적화에 유리한 기능은 웹 전용으로 신설, 초기 개발비용 증가 감수."

### 3.1 원칙

1. **CRUD 성격의 단일 리소스 API**(매장 수정, 직원 상세, 급여 상세 조회 등)는 기존 `com.rich.sodam.controller.*`를 그대로 호출한다. 모바일과 요청/응답 스키마를 공유해 백엔드 변경을 최소화한다.
2. **여러 API를 조합해야 하는 대시보드 집계 화면**(예: 사장 홈 대시보드 — 오늘 출퇴근 현황+대기 승인+매출 요약+알림을 한 화면에)은 웹 전용 BFF를 신설해 왕복(round-trip) 수를 줄인다.
3. **웹 특유의 인증/세션 처리**는 반드시 BFF를 거친다 (§4 참고) — 모바일 JWT 발급 경로와 충돌하지 않도록 격리.
4. BFF는 우선 **Next.js Route Handlers**(`app/api/**`)로 구현한다. Node.js 서버가 백엔드(7070)를 프록시/집계하는 방식이며, Spring 쪽에 신규 컨트롤러를 추가하지 않는 것이 기본값이다.
5. 다만 다음 경우는 **Spring 쪽에 `/api/web/**` 네임스페이스**를 신설한다 (Next.js BFF만으로 해결 안 되는 경우):
   - DB 트랜잭션 경계 안에서 여러 서비스를 묶어야 하는 집계(예: 급여 정산 마법사 3단계를 단일 트랜잭션 요약 API로)
   - 세션→내부 인증 컨텍스트 변환이 백엔드 내부에서 이뤄져야 하는 경우(§4)

상세 엔드포인트별 분류는 [02_API_활용계획.md](02_API_활용계획.md)에서 다룬다.

### 3.2 "웹앱 충돌 억제"의 구체적 의미

동일 사장이 모바일 앱과 웹 콘솔을 동시에 사용할 때 발생할 수 있는 문제:

- 모바일에서 스케줄 편집 중 웹에서 같은 시프트를 편집 → 낙관적 락으로 방지 ([05_동시성제어_및_고급아키텍처.md](05_동시성제어_및_고급아키텍처.md))
- 웹 세션과 모바일 JWT가 같은 사용자를 다르게 인증 → 백엔드 `SecurityContext`에 도달하는 시점에는 동일한 `Authentication` 형태로 정규화되어야 함 (§4.3)
- 웹에서만 존재하는 신규 API(BFF 집계 등)가 모바일 앱 API 계약에 영향을 주지 않도록 **네임스페이스 분리**(`/api/web/**`)로 충돌 표면적을 차단

## 4. 인증 아키텍처 — 웹 전용 세션/쿠키 신설

사용자 결정: "웹 전용 보안 배선 신설, 세션/쿠키 도입."

### 4.1 흐름

```
[브라우저] --로그인 폼--> [Next.js Route Handler /api/auth/login]
                                    |
                                    v
                      [Spring: POST /api/web/auth/login] (신규)
                                    |
                          검증 후 세션 생성(Redis)
                                    |
                                    v
                     Set-Cookie: sodam_web_sid=... (HttpOnly, Secure, SameSite=Strict)
                                    |
                                    v
                          [브라우저에 쿠키 저장]

이후 요청: [브라우저] --쿠키 자동첨부--> [Next.js] --세션ID→내부토큰 변환--> [Spring 기존 API]
```

### 4.2 백엔드 변경 범위

- 기존 `SecurityConfig`의 STATELESS JWT 필터체인은 **그대로 유지**(모바일 영향 없음).
- 신규로 세션 기반 인증 경로를 병행 지원: `Spring Session Data Redis`를 도입해 웹 세션을 Redis에 저장(이미 `spring-boot-starter-data-redis` 의존성 보유 — 신규 의존성 추가 최소화).
- **세션 전용 Redis 인스턴스를 물리적으로 분리**한다(기존 애플리케이션 캐시는 Ehcache가 담당하므로 실제로는 Redis를 처음 세션 용도로 본격 사용하는 셈이지만, 향후 캐시 목적으로 Redis가 추가 활용될 가능성을 감안해 처음부터 용도를 분리). 이유: 세션은 로그인 가용성에 직결되는 고가용성(HA) 대상이라 Sentinel/Cluster 이중화를 **초기 출시부터 적용**하기로 했는데([05_동시성제어_및_고급아키텍처.md](05_동시성제어_및_고급아키텍처.md) §4, [06_DB_마이그레이션계획.md](06_DB_마이그레이션계획.md) §4), 캐시성 데이터와 같은 인스턴스를 쓰면 캐시 재시작·flush 운영 작업이 세션(=로그인 상태)에까지 영향을 줄 수 있어 장애 격리 관점에서 분리가 안전하다.
- 신규 필터 또는 `SecurityFilterChain` 빈을 **경로 기준으로 분리**(`/api/web/**`는 세션 인증, 그 외는 기존 JWT 인증) — Spring Security의 다중 `SecurityFilterChain` 패턴 사용.
- 세션 인증이 성공하면 내부적으로 기존 JWT 클레임과 동일한 `Authentication` principal(사용자ID, role, storeId 등)을 구성해 `StoreAccessGuard`를 포함한 기존 인가 로직을 **변경 없이** 재사용한다. → 인가 계층 이원화를 피하는 것이 핵심 설계 목표.

### 4.3 왜 JWT 재사용이 아니라 세션인가 (근거)

- 웹은 XSS 위협 표면이 모바일보다 넓다(서드파티 스크립트, 브라우저 확장 등) — `localStorage`에 JWT를 두는 방식은 탈취 위험이 큼.
- `HttpOnly` 쿠키는 JS에서 읽을 수 없어 XSS로 인한 토큰 탈취를 원천 차단.
- 세션은 서버측 즉시 무효화(강제 로그아웃, 기기 revoke)가 JWT 블랙리스트 방식보다 단순.
- 대신 CSRF 방어가 필수로 따라온다 — [04_보안정책.md](04_보안정책.md) §2.

### 4.4 웹소켓 인증

기존 STOMP `/ws`는 CONNECT 프레임에 JWT를 담아 인증한다. 웹 콘솔은 세션 쿠키만 가지고 있으므로, 브라우저가 WebSocket 핸드셰이크 시 쿠키를 자동 전송하는 특성을 활용해 **CONNECT 인터셉터가 세션ID→내부 Authentication으로 변환**하도록 백엔드에 분기를 추가한다(§4.2와 동일 원칙 재사용).

## 5. 배포 토폴로지 (제안)

```
                    ┌─────────────────────┐
   사장 브라우저 ───▶│  Next.js (Node 20)   │  포트 3000 (내부) / 443 (외부, 리버스프록시)
                    │  web-master.sodam.*  │
                    └──────────┬───────────┘
                               │ 프록시/BFF 집계 (Route Handlers)
                               ▼
                    ┌─────────────────────┐
                    │  Spring Boot 백엔드   │  포트 7070 (기존 고정, 변경 없음)
                    │  /api/**  (기존)      │
                    │  /api/web/** (신규)   │
                    └──────────┬───────────┘
                               │
                     ┌─────────┴─────────┐
                     ▼                   ▼
                  MySQL(13306)      Redis(16379) — 캐시 + 세션 스토어(신규 용도 추가)
```

- 백엔드 포트 7070은 절대 변경하지 않는다(CLAUDE.md 고정 규칙).
- 웹 프론트 도메인은 **`owner.sodam.app`으로 확정**한다.
- 개발환경: `docker-compose.yml`에 Next.js 서비스를 포함해 로컬 풀스택 기동을 통합한다(기존 `docker compose up -d` 한 번으로 BE+FE+MySQL+Redis+웹콘솔이 함께 뜨는 방식 — 신규 팀원 온보딩 비용 최소화가 우선이라고 판단, [07_배포_운영계획.md](07_배포_운영계획.md) §2 참고). 단 로컬 개발 중 Hot Reload 속도를 위해 `npm run dev` 단독 구동도 계속 지원한다.
- 웹 프로젝트는 기존 모노레포(`Project_sodam/`) 내 신규 최상위 디렉터리 `web-master/`로 둔다 — 이유: 이 리포지토리는 이미 `CLAUDE.md` 하나로 FE·BE 규칙을 통합 거버넌스하고 있고, API 계약 변경처럼 웹·백엔드를 함께 건드리는 PR을 원자적으로 유지하는 이점이 별도 리포지토리 분리의 이점(독립 배포 주기, 독립 권한관리)보다 현재 팀 규모에서 크다고 판단([07_배포_운영계획.md](07_배포_운영계획.md) §8).

## 6. 실시간 동기화

기존 STOMP WebSocket(`/ws`, 토픽 `/topic/store.{storeId}`)을 그대로 재사용한다. 트랜잭션 `afterCommit` 발행 패턴도 변경하지 않는다. 웹 콘솔은 모바일과 동일 토픽을 구독해 사장이 웹을 보고 있는 동안 직원 출퇴근·직원 입사 등 이벤트가 실시간 반영되게 한다. 웹 특유의 브라우저 알림(Web Push)은 §4.9 요건에 따라 2차 검토(FCM과 별개 스택 필요).

## 7. 확정 (2026-07-26, 2차 확인)

- 도메인: `owner.sodam.app`
- 로컬 개발: `docker-compose.yml`에 Next.js 서비스 통합 + `npm run dev` 단독 구동 병행 지원
- Redis: 세션 전용 인스턴스 물리 분리, 초기 출시부터 Sentinel/Cluster HA 적용
- 저장소 구조: 별도 리포지토리 분리가 아닌 기존 모노레포 내 `web-master/` 신규 디렉터리
