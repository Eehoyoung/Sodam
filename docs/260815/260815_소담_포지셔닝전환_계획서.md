## 0. 왜 계획이 바뀌었는가 — 조사 결과 3줄

1. **알바몬 '보스몬'이 무료로 이미 들어와 있다.** GPS/QR 출퇴근, 스케줄, 급여 정산,
   근로계약서, 명세서, 문서함, 자동 출퇴근까지 전부 무료다. **기본 근태 레이어는 동등하다.**
2. **보스몬은 법 계산 깊이로 못 들어온다.** 무료 미끼 상품이고, 틀리면 알바몬 본체가 책임진다.
   게다가 "알바를 덜 뽑게 만드는 기능"은 채용 광고 매출과 이해충돌이라 구조적으로 불가능하다.
3. **정부가 5인 미만 사업장 근로기준법 전면 적용 로드맵을 발표했다** (2025.12 업무보고,
   2025 하반기~2028 단계적). **"우리 가게가 5인 미만인가"가 폭발적 수요가 된다.**

→ **결론: 근태 앱 경쟁에서 나오고, 법 판정 깊이로 간다.**

## 4. 작업 패키지

### ★ WP-1 · 상시근로자 수(근기법 기준) 산정 + 법적용 시뮬레이터 (최우선)

> 🔴 **경고 — 신규 구현이 아니다. 그리고 기존 로직을 재사용하면 안 된다.**
> `EmploymentCreditService`가 이미 상시근로자를 집계하지만 산식이 **"그 달 출근 기록이 있는
> 직원의 distinct 수"** 다. 근기법 시행령 §7의2는 **"산정기간 연인원 ÷ 가동일수"** 로 값이 다르다.
> (알바 4명이 주 2일씩 → distinct 4명 vs 근기법식 약 1.6명)
> **세액공제용 로직을 5인 경계 판정에 재사용하면 오판이 나고, 그 오판은 채용 결정을 바꾼다.**
> → 근기법 전용 산정기를 **별도 신설**하고, 이름부터 `taxCreditHeadcount` / `statutoryHeadcount`로
> 구분한다. `SubsidyStandards.HEADCOUNT_LIMIT`(10인, 두루누리)과 5인 경계를 혼동하지 않는다.

**개발량이 가장 작은데 차별화가 가장 크다. 데이터는 이미 다 있다.**

**3단 구성**

| 단 | 기능 | 출력 예시 |
|---|---|---|
| ① 현재 참고 산정 | 근기법 시행령 §7의2 방식 (산정기간 연인원 ÷ 가동일수) | "이번 달 참고 산정 4.3명 — 5인 미만에 해당할 가능성" |
| ② **전환 경고** | 직원 1명 추가 시 임계 초과 여부 시뮬레이션 | "1명 더 채용하면 5인 이상에 해당할 가능성이 있습니다. 가산수당·연차·부당해고 제한이 새로 적용될 수 있어요" |
| ③ 로드맵 타임라인 | 정부 추진 단계별 적용 예정 항목 | "정부 추진 로드맵상 2027년경 연차유급휴가 확대가 검토되고 있습니다" |

**구현 원칙**
- `LaborRiskService`에 `HEADCOUNT_THRESHOLD` RiskType 추가. **신규 테이블 없음**
- 산정 파라미터(산정기간·가동일수 정의)는 `core/payroll/constant/`에 상수로 분리.
  서비스 안에 하드코딩 금지 — 노무사 회신(`G-18`) 후 상수만 바꾸면 되게
- **화면에 면책 문구 상시 노출**: "참고 산정이며 최종 판단은 근로감독관·법원의 권한입니다"
- ②의 인건비 영향 추정은 **범위(약 ○○~○○만원)** 로 표시. 단일 금액 확언 금지
- ③의 로드맵 데이터는 **설정 파일로 분리**. 법령이 바뀌면 코드 배포 없이 갱신 가능해야 함

**⚠️ 금지**: 상시근로자 수를 근거로 다른 기능을 자동으로 켜거나 끄지 않는다.
(예: "5인 이상이니 연차 기능 자동 활성화" ← 금지. 오판 시 급여가 틀어진다)

### WP-2 · 사후 감지 → 사전 예측 전환

현재 규칙은 "지금 이미 그런 상태"를 잡는다. 예방하려면 **확정 시프트를 미리 돌려봐야 한다.**

| RiskType | 판정 | 트리거 | Severity |
|---|---|---|---|
| `SCHEDULE_52H_FORECAST` | 확정 시프트만으로 주 52h 초과 예상 | 스케줄 확정 시 | DANGER |
| `SCHEDULE_15H_SHORTFALL` | 확정 시프트 15h 미만 → 주휴 미발생 | 스케줄 확정 시 | WARN |
| `BREAK_MISSING_FORECAST` | 4h→30분 / 8h→1h 휴게 미배치 | 스케줄 확정 시 | WARN |
| `MINOR_NIGHT_FORECAST` | 미성년 시프트가 22~06시에 걸침 | 스케줄 확정 시 | DANGER |
| `MINOR_HOURS_FORECAST` | 미성년 1일 7h / 주 35h 초과 예상 | 스케줄 확정 시 | DANGER |

**구현 원칙**
- 판정 상수는 `LaborLawConstants`·`MinorLaborStandards`·`MinimumWage`만 참조
- 스케줄 확정(`WorkShiftService`/`FixedScheduleService`) 이후 진단 → **`LiveSyncPublisher`**(내부에서
  `AfterCommitExecutor` 사용)를 재사용해 `/topic/store.{storeId}` + FCM 발행.
  **`TransactionSynchronization`을 직접 구현하지 않는다. 신규 알림 채널도 만들지 않는다**
- ⚠️ **52h 중복 억제**: `CONTRACT_OVER_52H`(기존)·`SCHEDULE_52H_FORECAST`(신규)·`WEEKLY_52H_NEAR`(기존)이
  겹친다. 같은 직원·같은 주에 2개 이상이면 **가장 심각한 1건만 노출**한다.
  우선순위 `CONTRACT_OVER_52H` > `SCHEDULE_52H_FORECAST` > `WEEKLY_52H_NEAR`
- **DANGER여도 확정을 막지 않는다.** 경고만 띄우고 사장이 결정한다

### WP-4 · 자연어 설명 계층 `LaborRiskNarrator`

**기존 `ReceiptOcrClient` 패턴을 그대로 복제한다.**
실제 위치는 `config/integration/`이 아니라 **`service/`** 다. `LaborRiskNarrator`도 `service/`에 둔다.

```
LaborRiskNarrator (interface)
├── TemplateLaborRiskNarrator   ← 기본 빈. 외부 호출 0. 이것만으로 완전 동작
└── LlmLaborRiskNarrator        ← sodam.ai.provider 설정 시에만 로드
```

**제약**
- `sodam.ai.provider` 미설정이 기본 → Template이 응답. **외부 API 없이 100% 동작**
- LLM 페이로드는 **비식별 집계값만**. 직원명·전화·주소·계좌·`employeeId` 금지, 익명 라벨(`직원A`)
- LLM은 **표현만** 담당. 숫자·RiskType·Severity는 규칙 엔진 값 그대로. 판정을 바꾸면 버그
- 출력 문구를 §1 표현 규칙으로 **후처리 검증**. 금지어 포함 시 Template 폴백
- LLM 실패 시 fail-safe Template 폴백. 기능 중단 금지
- 유료 실키 활성화는 인간 승인 — 신규 게이트 `H-6`

> **심사 대응**: "AI를 쓴다"가 아니라 **"AI가 죽어도 제품은 돈다"** 는 설계다.

### WP-6 · 경력증명서 표면화 (신규)

**세상에 없는 문서다.** 알바생이 3년간 4곳에서 일해도 증명할 방법이 없다.
소담은 실제 출퇴근으로 검증된 시간을 갖고 있으므로 발급할 수 있다.
**경쟁사는 데이터가 매장에 귀속되어 구조적으로 불가능하다.**

- 기존 `certificate` 도메인을 **근로자 진입 동선에 노출** (현재 묻혀 있음)
- 퇴사 후에도 본인 스코프로 조회·발급 가능 (PRD §4.14 인가 규칙 준수)
- **증명력 구분 필수** (PRD §4.14 기존 규칙 그대로):
  - 매장 기록 → 제3자(사업주) 확인이 있는 기록
  - 개인 모드 자기신고 기록 → **증명서 발급 대상 아님.** PDF에도 라벨 표기
- v1 **무과금**. 유료 직업소개는 직업안정법 등록 대상이므로 과금 배선 금지

### WP-8 · 가격 구조 배선 (⚠️ 실행이 아니라 배선만)

시장 조사 결과 현행 가격이 저평가돼 있다. **다만 지금 올리지 않는다.**
심사 제출용은 현행가를 유지하고, **A/B 실측이 가능한 구조만 만든다.**

| 티어 | 현행 | 검토안 | 비고 |
|---|---:|---:|---|
| FREE | 0 / 2명 | 0 / **1명** | 직원 보유 매장 평균이 2.4명 — 2명 상한은 경계에 걸침 |
| STARTER | 9,900 | **14,900** | 뉴플로이의 41%, 시프티 Standard의 71% — 여전히 가격 우위 |
| PRO | 19,900 | **29,900** | |
| PREMIUM | 39,900 | **폐지 검토** | 4티어는 선택 피로. 3티어가 전환율에 유리 |

**구현 범위 (이번에 할 것)**
- 가격·상한을 `PlanType` enum에서 **설정으로 분리**. 코드 배포 없이 변경 가능하게
- **Grandfathering 구조**: 가입 시점 가격을 구독 레코드에 고정 저장.
  이후 가격이 바뀌어도 기존 가입자는 가입가 유지
- A/B 실험용 가격군 배정 필드 (베타 실측용)
- **DB 변경 필요 시 `V92__` 이상 신규 파일**

**⚠️ 하지 말 것**
- 실제 가격 숫자 변경 (인간 승인 사항 — 신규 게이트 `H-7`)
- `PlanType` enum의 **선언 순서 변경·중간 삽입** (PRD §4.8 명시 금지사항)

## 7. 심사 데모 시나리오 (90초 — 이 흐름이 나오도록 구현한다)

1. 사장이 다음 주 스케줄을 짠다. 직원 A에게 무심코 주 54시간을 배정한다.
2. **확정 버튼을 누르는 순간** 경고 —
   "직원A의 다음 주 근무가 54시간입니다. 주 52시간을 초과할 가능성이 있어요."
3. 사장이 2시간을 덜어낸다. 홈의 "확인 필요 3건"이 **2건**으로 줄어든다.
4. **사장이 알바 1명을 더 등록하려 한다. 두 번째 경고가 뜬다** —
   "1명 더 채용하면 상시근로자 5인 이상에 해당할 가능성이 있습니다.
    가산수당·연차·부당해고 제한이 새로 적용될 수 있어요. 월 인건비 영향 약 ○○~○○만원."
5. 내레이션:
   > **"경쟁 서비스는 알바를 더 뽑게 만들어야 돈을 법니다.
   > 소담은 사장님이 법을 어기지 않게 만들어야 돈을 법니다."**

**4단계가 이번 계획의 존재 이유다.** 어떤 경쟁사도 이 경고를 만들 수 없다 —
채용을 줄이는 기능은 채용 광고 매출과 이해충돌이기 때문이다.
