# 260816 · 포지셔닝 전환(260815) 후속 작업 계획서

> 전신 문서: `docs/260815/260815_소담_포지셔닝전환_계획서.md`(WP-1~WP-9, 전부 구현·테스트·문서 반영 완료,
> 커밋 `d97b230`~`27dbde8`). 그 작업을 마치고 나서 남은 것 — 다음 세션이 이어받을 목록이다.
>
> **분류 원칙**: 사람의 승인·전문가 회신 없이 **우리가 시간만 내면 끝나는 것**은 여기(코드 작업
> 계획서)에 WP로 남긴다. 노무사·법무 회신, 인간 승인, 출시 전 검증·산출물처럼 **외부 요인이 걸린
> 것**은 `docs/RELEASE_GATES.md`에 게이트(V-6·D-7)로 등록했다 — 이 문서와 함께 갱신한다.

## 0. 왜 이 목록이 나왔는가

260815 작업은 계획서 기준 9개 WP를 전부 구현했지만, 진행 중 두 가지 종류의 갭이 새로 드러났다.

1. **백엔드는 있는데 프론트가 없다** — WP-1(상시근로자 시뮬레이터)·WP-7(노무 건강도 요약 API)
   둘 다 컨트롤러·서비스·테스트까지 완성했지만, **어느 화면도 그 엔드포인트를 호출하지 않는다**
   (`grep -rl "labor-health\|statutory-headcount" frontend/src` → 0건, 260816 재확인). 데모
   시나리오 4단계("알바 1명 추가 시 5인 경계 경고")는 사실 지금 **재현 불가능**하다 — 백엔드 API는
   있지만 그걸 부르는 UI가 없기 때문이다.
2. **의도적으로 범위를 좁힌 지점** — WP-5(개인정보 처리 차단)는 조회 전용 경고까지만 구현하고
   실제 쓰기 경로 차단은 "노무사 회신 후 판단"으로 보류했다. 이건 새로 발견한 문제가 아니라
   260815 세션에서 이미 인지하고 기록해 둔 결정인데, 실행이 안 됐으니 후속에 다시 올린다.

## 1. WP-A · 상시근로자 시뮬레이션 FE 배선 (P0, 데모 필수)

**우선순위가 가장 높다.** 이게 안 되면 260815 작업의 핵심 데모 포인트(§7 4단계)가 안 열린다.

### 배경

- `GET /api/stores/{storeId}/labor-risk/statutory-headcount` — 현재 참고 산정 + 확대적용 로드맵.
  구현·테스트 완료(`StatutoryHeadcountServiceTest`), FE 소비처 0건
- `GET /api/stores/{storeId}/labor-risk/statutory-headcount/simulate?additionalEmployees=N` —
  직원 N명 추가 시뮬레이션(경계 초과 여부·신규 적용 조항·인건비 영향 범위). 구현·테스트 완료,
  FE 소비처 0건

### 작업

1. `frontend/src/features/risk/services/riskService.ts`에 두 엔드포인트 fetch 함수 추가
   (`fetchStatutoryHeadcount`, `simulateStatutoryHeadcount`) — 기존 `fetchLaborRisks` 패턴 그대로
2. **현재 참고 산정 + 로드맵 화면** — 신규 또는 `LaborRiskDashboardScreen` 상단에 카드로 배치.
   "이번 달 참고 산정 4.3명" + 로드맵 타임라인(`roadmap[]`, "정부가 추진 중"이라는 표현 그대로
   노출 — HC-2 위반 금지, 절대 확정 시행일처럼 보이게 재구성하지 말 것)
3. **직원 추가 등록 진입점에 시뮬레이션 훅** — 정확한 화면은 착수 시 재확인하되 유력 후보는
   `EmployeeManagementScreen.tsx`(사장의 직원 관리) 또는 `StoreDetailScreen.tsx`의 초대코드 발급
   지점. "직원을 추가하시겠어요?" 같은 확인 단계에서 `simulate?additionalEmployees=1` 결과를
   먼저 보여주고, **등록 자체는 막지 않는다**(HC-5 — 경고는 차단이 아니다. 사장이 결정)
4. 표현 규칙(HC-1·HC-2) 그대로 적용 — "5인 이상입니다" 금지, "5인 이상에 해당할 가능성이
   있습니다"만 사용. 인건비 영향은 범위(`estimatedMonthlyCostMin`~`Max`)로만 표시, 단일 금액 금지

### done_when

- [ ] 데모 시나리오(계획서 §7) 4단계가 실제 화면 조작으로 재현됨(에뮬레이터)
- [ ] 로드맵 항목에 "정부가 추진 중"류 표현 유지 확인(HC-2 grep)
- [ ] 시뮬레이션 결과가 등록 자체를 막지 않는 테스트(HC-5) — FE 레벨(화면 테스트) + 이미 있는
      BE 레벨(`WorkShiftServiceTest`의 HC-5 패턴 참고)
- [ ] `npm run lint`/`npm run test:unit` green, 신규 코드에 `any` 추가 없음

이 WP를 마치면 [[V-6]](`docs/RELEASE_GATES.md`)이 자동으로 해소 조건을 충족한다 — V-6은 이 WP의
완료 여부를 추적하는 게이트다.

## 2. WP-B · 노무 건강도(`labor-health`) API 활용 방향 결정 + 배선 (P1)

### 배경

WP-7에서 신설한 `GET /api/stores/{storeId}/labor-health`(BASIC, 건수만)·`/labor-health/detail`
(FULL, 설명까지)는 플랜 게이팅(402+errorCode) 인프라를 증명하려고 만들었다. 하지만 실제 사장 홈
카드(`OwnerDashboardScreen`)는 **게이팅이 없는** WP-1의 `/labor-risk`를 그대로 쓴다(데모·시드
계정 의존성을 피하려는 260815의 의도적 선택, 커밋 `d9d9c80` 메시지에 명시).

결과적으로 `LaborHealthController`의 두 엔드포인트는 **테스트만 있고 실사용처가 없는 고아
API**다. 이대로 두면 "쓰지 않는 코드"가 늘어나는 것과 같다.

### 결정이 필요한 것 (D-7로 게이트 등록, §3 참조)

- **안 A**: 사장 홈 카드를 `/labor-health`로 전환해 실제로 FREE/STARTER를 건수만, PRO 이상을
  설명까지 차등 노출한다. 대신 FREE·STARTER 시드 계정에서 데모가 "건수만" 보이는 것을 받아들여야
  한다
- **안 B**: 홈 카드는 지금처럼 게이팅 없이 유지(항상 완전한 정보), `/labor-health`는 별도 "상세
  분석" 화면에서만 써서 실제 업셀 지점으로 삼는다
- **안 C**: 당장은 쓰지 않고 인프라만 보유(현재 상태 유지) — 다만 이 경우 "쓰지 않는 API"라는
  기술 부채로 `docs/RELEASE_GATES.md` §8 T에 등록해야 한다

### 작업 (D-7 결정 이후 착수)

1. 결정안에 맞춰 FE 서비스 함수(`fetchLaborHealth`/`fetchLaborHealthDetail`) 추가
2. 안 A 채택 시 402 응답 처리(페이월 유도 UI) — 기존 `PastDueBanner` 패턴 참고
3. 안 B 채택 시 신규 "노무 리스크 상세 분석" 화면 설계

## 3. WP-C · minorguard 개인정보 처리 실제 차단 (P1, G-17 회신 후 착수)

### 배경

260815 WP-5에서 `MinorLaborGuardService.evaluate()`가 만 14세 미만 + 친권자 동의서 미확인 시
`personalDataProcessingBlocked=true` 경고 플래그를 반환하도록 구현했지만, 이 서비스는 **조회
전용**이라 실제 등록·근무기록 등 **쓰기 경로를 코드로 차단하지 않는다**(코드 주석에 명시,
`MinorLaborGuardService.java` 클래스 javadoc 참조).

### 왜 지금 안 하는가

어느 쓰기 경로까지 하드 차단을 걸지가 그 자체로 노무사·법무 판단 영역이다(G-17). 잘못 넓게
막으면 정상적인 미성년 직원 등록 자체가 막히고, 잘못 좁게 막으면 §22의2 요건을 충족 못 한다.

### G-17 회신 후 작업

1. 회신에서 확정된 범위에 맞춰 차단 지점 특정(후보: 직원 초대코드 승인 시점, 출퇴근 최초 기록
   시점, 근로계약서 생성 시점 — 회신에 따라 달라짐)
2. 차단 시 사장에게 노출할 안내 문구(HC-1 톤 유지, "차단됐습니다"가 아니라 "먼저 동의서를
   등록해 주세요" 류)
3. 이미 등록된 만 14세 미만 직원(동의서 미확인) 소급 처리 정책 필요 — 기존 데이터 마이그레이션이
   아니라 **운영 판단**(강제 비활성화 vs 경고만 유지) 필요, 이것도 G-17 범위에 포함해 함께 질의

## 4. WP-D · 가격 A/B 실험 그룹 배정 로직 설계 (P2)

### 배경

WP-8에서 `Subscription.priceVariant` 컬럼(A/B 가격 실험 그룹)을 마련했지만 **어디서도 실제
배정하지 않는다**(`grep -rn "assignPriceVariant" backend/src/main` → 0건, 260816 확인). 값
자체(H-7)와 무관하게 **배정 메커니즘**은 지금 설계해도 된다 — 결정되지 않은 건 "얼마로 보여줄까"
지 "누구를 A/B로 나눌까"가 아니다.

### 작업 (가격 숫자 변경 없이 진행 가능)

1. 배정 기준 설계 — 가입일·userId 해시·랜덤 등 어떤 방식으로 그룹을 나눌지
2. `SubscriptionService.subscribe()`에서 `pending.assignPriceVariant(...)` 호출 지점 추가
3. **주의**: 그룹을 나누는 것과 그룹별로 다른 가격을 청구하는 것은 다른 일이다. 이 WP는 배정만
   하고, 실제로 그룹에 따라 다른 금액을 `PlanPricingService`가 반환하게 만드는 건 H-7 승인 이후
4. 실험 결과 집계 쿼리(어느 그룹의 전환율이 높은지) — `DomainEventService` 기존 인프라 재사용
   검토, 신규 집계 테이블 만들기 전에 먼저 확인

## 5. WP-E · 신규 화면 테스트 커버리지 보강 (P2, 낮은 위험도)

260815에서 서비스·컨트롤러 레벨 테스트는 촘촘히 붙였지만(BE 신규 테스트 다수, FE는 서비스
레벨만) 화면 렌더 레벨 jest 테스트가 빠진 곳이 있다.

| 화면 | 현재 상태 |
|---|---|
| `LaborRiskDashboardScreen.tsx` | 서비스(`riskService.ts`) 테스트 없음, 화면 렌더 테스트 없음 |
| `MyCertificateScreen.tsx` | 화면 렌더 테스트 없음(백엔드 `CertificateServiceTest`는 있음) |
| `MinorGuardScreen.tsx` | 화면 렌더 테스트 없음(서비스 테스트는 WP-5에서 추가함) |

급하지 않다 — 세 화면 다 수동 검증(lint+tsc+기존 통합 테스트)은 이미 통과했다. 회귀 방지 차원의
보강 작업.
