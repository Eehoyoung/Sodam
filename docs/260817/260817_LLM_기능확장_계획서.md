> 260815~16 포지셔닝 전환(근태앱→노무 리스크 사전예측) 작업 중 처음으로 LLM(Anthropic)이
> 코드베이스에 등장했다. 이 문서는 그 배선을 다른 도메인으로 넓힐 수 있는지 조사한 결과다.

> 법무/노무 선행 필요)은 `docs/RELEASE_GATES.md`의 **T-17~T-19·G-20**으로 이관했다.
>
> **2026-08-17 재검토 정정**: 원안의 WP-1(교대 요청 사유 도우미)·WP-3(구직 자기소개 도우미)이
> 가리킨 화면·필드가 실제 코드에 없었다. `ShiftSwapController`의 대타 모집 흐름(`POST

> 설정 화면(`JobSeekingSettingsScreen`)도 칩·지역선택·요일선택뿐 자기소개 텍스트 필드가 없다.
> 코드에 실존하는 자유 텍스트 필드로 교체했다(아래 WP-1·WP-3).

## 1. 배경 — 현재 LLM 배선

`LlmLaborRiskNarrator`(`backend/src/main/java/com/rich/sodam/service/LlmLaborRiskNarrator.java`)
딱 하나뿐이다. 역할은 "규칙엔진이 이미 확정한 노무 리스크 문구를 자연스럽게 다듬기"이며,
`LaborRiskNarrator` 인터페이스의 두 구현체 중 하나다(기본은 `TemplateLaborRiskNarrator`,
외부 호출 0건).

- **활성 조건**: `sodam.ai.provider=anthropic`일 때만 스프링 빈으로 등록. 유료 실키 활성화는
  **[[H-6]] 게이트로 인간 승인 대기 중**(2026-08-17 기준 미활성) — 아래 WP-1~5는 전부
  **H-6 활성화 이후 실행**을 전제로 한다. 지금 당장 LLM을 켜자는 문서가 아니다.
- **모델**: 기본값 `claude-haiku-4-5-20251001`(설정 가능)

## 2. 재사용 패턴

`LlmLaborRiskNarrator`가 이미 증명한 4단계 패턴을 새 도메인에도 그대로 적용한다:

1. **비식별화** — 직원명 등 PII를 익명 라벨(예: `"직원A"`)로 치환한 뒤에만 LLM에 전송(HC-8)
2. **LLM 호출** — "말투만 다듬어라, 숫자·사실관계는 바꾸지 마라"를 프롬프트에 명시
3. **검증** — 응답에 금지어(HC-1: "위반입니다"·"막아드립니다"·"정확하게 계산"·"법적 자문"·
   "안전합니다" 등, HC-2: 미확정 정책 확정처럼 말하기)가 없는지, 원래 수치가 그대로 보존됐는지
   확인
4. **실패 안전 폴백** — 네트워크·파싱·검증 실패는 전부 흡수하고 원본(템플릿) 문구를 반환 —
   LLM이 죽어도 화면은 정상 동작

WP마다 "이 패턴에서 무엇을 그대로 쓰고 무엇을 새로 설계해야 하는가"를 명시한다.

## 3. WP 목록 (우선순위 순)

### WP-1. 출퇴근 정정 요청 사유 다듬기 (직원용)

- **대상**: `frontend/src/features/attendance/screens/AttendanceCorrectionRequestScreen.tsx`
  (정정 사유 자유 입력, 5~200자) · 백엔드 `AttendanceCorrectionRequest.reason`
- **필요 데이터**: 정정 사유 텍스트뿐(제안 출퇴근 시각은 이미 구조화 데이터라 별도 전송 불요)
- **PII**: 거의 없음 — 화면 자체가 "사장님과 직원 본인만 볼 수 있어요"라고 이미 스코프를
  좁혀뒀고, 사유 텍스트에 타인 실명이 섞일 가능성은 낮음(그래도 검증 단계에서 인명 패턴이
  보이면 폴백하도록 방어)
- **검증 로직**: 기존 4단계 패턴 그대로 재사용 — 신규 설계 불필요. **가장 작은 파일럿**으로
  적합(노무 리스크 도메인 밖에서도 패턴이 통하는지 첫 검증)
- **완료 기준**: 사유 입력 필드에 "다듬기" 버튼 → LLM 응답으로 교체 제안, 실패 시 원본 유지.
  자동테스트로 폴백 경로(네트워크 실패·금지어 검출) 커버

### WP-2. 사장 주간 브리핑

- **대상**: `WeeklyInsightsResponse`(backend dto/response), `StoreInsightsController`의
  `/weekly` 엔드포인트 응답(이벤트 종류별 카운트만 — `InsightItem(eventType, label, count)`)
- **필요 데이터**: 순수 집계 카운트뿐, 개인 식별 정보 없음
- **PII**: 0건 — 비식별화 단계 자체가 불필요
- **검증 로직**: 수치 보존 검증은 그대로 재사용(카운트 값이 바뀌면 안 됨). 금지어 검증도
  동일. **비식별화 단계만 스킵**하면 되는 가장 단순한 확장
- **완료 기준**: 사장 홈 화면에 "이번 주 요약" 문장 카드 추가, LLM 미활성 시 기존 숫자
  나열형 표시로 폴백

### WP-3. 채용 지원 메시지 다듬기 (직원용)

- **대상**: `frontend/src/features/recruitment/screens/JobPostingDetailScreen.tsx`(공고 지원 시
  자유 메시지 입력) · 백엔드 `JobApplication.message`(200자 제한)
- **필요 데이터**: 지원 메시지 텍스트 + 지원 대상 공고의 근무형태·업종(맥락용, 구조화 데이터)
- **PII**: 낮음 — 지원자가 자유롭게 쓰는 문구라 이름·연락처가 자연스럽게 섞여 들어갈 수 있음
  → WP-1과 달리 **비식별화 단계 없이는 바로 재사용 불가**, 인명·전화번호 패턴 탐지 후 마스킹
  하는 전처리를 검증 단계 앞에 추가해야 함(그래도 급여·계약처럼 구조화 PII 마스킹 대비는
  훨씬 가볍다)
- **검증 로직**: 기존 4단계 패턴 재사용 + 위 전처리(패턴 탐지 마스킹) 추가. "다듬기"이지 신규
  생성이 아니므로 원문 대비 사실관계(지원자가 적은 내용)가 바뀌지 않았는지 확인
- **완료 기준**: 지원 메시지 입력창에 "다듬기" 버튼 → 제안 문구로 교체, 실패 시 원본 유지.
  인명·전화번호 패턴이 포함된 입력에 대한 마스킹 테스트 포함

### WP-4. 채용공고 문구 생성 (사장용)

- **대상**: `JobPostingUpsertRequest`(backend dto/request, `message` 필드 — 200자 제한)
- **필요 데이터**: 근무형태·업종·근무일시·시급 등 구조화 입력
- **PII**: 없음
- **검증 로직**: 기존 금지어 검증(HC-1/HC-2)에 더해 **신규 검증 필요** — 남녀고용평등법·
  연령차별금지법이 금지하는 표현(성별·나이 선호 문구 등)을 걸러내는 별도 어휘 검증을
  설계해야 한다. 이 프로젝트 문서에 지금까지 없던 새 법적 제약이라 **검증 규칙 확정 전
  법무 확인을 권장**(WP 자체는 착수 가능하나, 검증 규칙 리스트는 법무 리뷰 후 확정)
- **완료 기준**: 200자 소개문 초안 생성 + 차별 표현 검증 테스트(양성 사례 통과, 음성 사례
  차단)

### WP-5. 매입장부 인사이트 코멘트 (사장용)

- **필요 데이터**: 거래처명·기간별 합계·비중, 품목 단가 추이 — 개인정보 아님(사업자 정보
