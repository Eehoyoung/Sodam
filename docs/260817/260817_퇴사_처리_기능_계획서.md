# 퇴사 처리 기능 계획서 (2026-08-17)

> 직전 세션의 "퇴사 처리 로직 코드 감사"(아티팩트 보고) 결과를 바탕으로 작성했다. 감사 결론은
> "지금 있는 건 사장이 누르는 비활성화 스위치 하나뿐"이었다 — 사직서 제출 경로가 없고, 매니저
> 전결이 붙어 있지 않고, 퇴사일이라는 업무상 날짜 자체가 없다.
>
> 이 문서는 그 갭 중 **게이트 밖에서 지금 착수 가능한 부분만** 다룬다(WP-1~5). 급여 계산·
> 보존기간 기산에 손대는 부분은 이미 `docs/RELEASE_GATES.md`에 G-15·G-6·L-1로 등록돼 있으므로
> **새 ID를 만들지 않고 그 게이트를 그대로 참조**하며, 회신 전에는 착수하지 않는다.
>
> **2026-08-17 1차 Opus 감사 반영**: 사직 수리(acknowledge)는 근로계약 종료 의사표시 수리(민법
> §660)라 `CONTRACT_MANAGE`의 실질에 가깝다는 지적을 받아 **사장 전용으로 축소**했다. "거절
> (REJECTED)" 상태도 삭제 — 사직은 근로자의 일방적 의사표시라 사용자가 거부할 수 없다.
>
> **2026-08-17 2차 확장(사용자 요청)**: 퇴사일 조율(WP-3)·양측 전자서명(WP-4)·화면 설계(WP-5)를
> 추가했다.
>
> **2026-08-17 3차 Opus 감사 반영(이번 정정)**: 2차 확장에서 실제 코드 대비 사실오류·설계 결함
> 4건이 나와 아래 §3-A·§4·§5를 다시 고쳤다 — ① WP-3의 이력 없는 3필드 덮어쓰기 모델을 append-only
> 제안 이력 엔티티로 교체, ② `ElectronicSignatureRetentionPolicies`가 자동 상속이 아니라 subjectType별
> 전용 컴포넌트가 필요함을 반영(신규 컴포넌트 작업 추가), ③ 전자서명 통합이 기본 `mode=off`(사람
> 승인 전까지 코어 서비스 빈 자체가 없음)라는 사실을 반영해 **서명 완료를 확인(acknowledge)의
> 하드 전제조건에서 제외**(fail-safe), ④ 서명 문서 문구는 기존 [[L-3]] 게이트(노무 문구·근로계약서
> 법적 검토 미완료) 대상임을 명시하고 신규 [[C-6]] 게이트로 등록.

## 1. 게이트 확인 (착수 전 필독)

|---|---|---|

| **[[G-6]]** | 근로기록 보존기간 기산일 | 보존기간 로직 자체는 건드리지 않되, **WP-4가 만드는 신규 서명 증적에는 신규 보존정책 컴포넌트가 필요**하다(§4 — 이건 "기산일 로직 변경"이 아니라 "기존 정책 패턴을 새 문서 유형에 반복 적용"이라 G-6과 결이 다르다) |

**결론**: WP-2는 게이트 밖에서 안전하게 착수 가능. WP-1·WP-3·WP-4는 전 과정을 **사장 전용**으로
설계해 착수한다. WP-4의 서명 문서 문구는 L-3/C-6 확정 전까지 **가안(假案) 상태로 유보**한다(§4).
이 판단 자체가 사용자 확인 대상이다.

## 1-A. 법령 근거 확인 (2026-08-17 WebSearch, 사용자 요청)

### 근로기준법 제36조(금품 청산) — 명문 규정, 확실

> "사용자는 근로자가 사망 또는 퇴직한 경우에는 그 지급 사유가 발생한 때부터 **14일 이내**에 임금,
> 보상금, 그 밖의 모든 금품을 지급하여야 한다. 다만, 특별한 사정이 있을 경우에는 당사자 사이의
> 합의에 의하여 기일을 연장할 수 있다."

출처: [국가법령정보센터 근로기준법 제36조](https://www.law.go.kr/LSW//lsLinkCommonInfo.do?lsJoLnkSeq=1025590515&chrClsCd=010202), [찾기쉬운 생활법령정보 — 금품청산](https://easylaw.go.kr/CSP/CnpClsMain.laf?popMenu=ov&csmSeq=1694&ccfNo=2&cciNo=2&cnpClsNo=2). 위반 시 3년 이하 징역 또는 3천만원 이하 벌금(형사처벌 대상).
**이 조문의 존재와 14일이라는 숫자는 명문 규정이라 확정 사실로 취급한다.**

### "퇴직일 = 마지막 근무일의 다음날" — ⚠️ 명문 정의 아님, 통계가 아니라 **적용 국면이 다른 것**

WebSearch·WebFetch로 3개 출처를 대조했는데 서로 다른 답을 준다. **정정**: 1차 작성 시 "2대1로
다음날 설이 우세"처럼 다수결로 읽힐 여지가 있었는데, 정확히는 **어느 법령 국면을 보느냐에 따라
답이 갈리는 것**이지 우열 문제가 아니다.

| 국면 | 답 | 근거 |
|---|---|---|
| 고용보험 자격상실일 | 이직일(마지막 근무일)의 **다음날** | 고용보험법 제14조 명문 |
| 국민연금 자격상실일 | 근로관계 종료일과 **같은 날** | [이코노믹리뷰 전문가 칼럼](https://www.economicreview.kr/) |
| 건강보험 자격상실일 | 근로관계 종료 **다음날** | 같은 칼럼 |
| "퇴직일" 자체(근로기준법) | **명문 정의 없음** — 판례·행정해석은 대체로 마지막 근무일과 **같은 날**로 취급 | 같은 칼럼 |

**결론(HC-1 톤 유지)**: "퇴직일=마지막 근무일 다음날"은 **고용보험 자격상실일 산정이라는 좁은
국면에서만** 명문 근거(고용보험법 §14)가 있고, 그 국면을 벗어나면(국민연금·근로기준법상 "퇴직일"
자체) 같은 날로 보는 해석이 오히려 더 일반적이다. 이는 G-15가 "퇴사일이라는 업무상 날짜 자체가
없다"고 지적한 것과 같은 문제의 다른 얼굴이다 — **이 계획은 이 불확실성을 코드로 확정하지 않는다.**
화면·서명 문서 어디에도 "이날부터 ~됩니다" 류의 단정적 안내를 넣지 않는다(HC-11).

### 14일 지급 기한 — 정보 제공까지만, 신규 게이트 불필요

WP-4의 서명 문서에 근로기준법 §36을 **그대로 인용하는 안내 문구**는 문제없다. 그러나 실제 지급
마감을 시스템이 강제(마감 알림·경고·차단)하는 기능은 범위 밖이다 — 지급 대상 금액 자체가 G-15에
걸려 있어, 얼마를 지급해야 하는지 모르는 채로 마감 경고를 만들면 잘못된 확신을 준다. 새 게이트 ID는
등록하지 않는다.

## 3. WP-1 — 직원 사직서 제출 기능 신설

기존 `AttendanceCorrectionRequest`의 **코딩 컨벤션**(엔티티 스타일, 낙관적 락, 상태 enum 패턴,
서비스·컨트롤러 계층 구조)은 참고하되, **상태 모델 자체는 신규**다 — 사직서는 정정 요청과 법적
성질이 다르다.

### 신규 엔티티: `EmployeeResignationRequest`

```java
@Entity
public class EmployeeResignationRequest {
    Long id;
    EmployeeStoreRelation relation;      // 어느 매장 소속에 대한 신청인지
    User requester;                       // 신청한 직원 본인
    LocalDate desiredResignationDate;     // 최초 희망일 — 데이터 캡처 전용(HC-1)
    LocalDate agreedResignationDate;      // 합의 확정일(nullable) — WP-3에서 채움, 역시 데이터 캡처 전용
    String reason;                        // 사유(선택, 200자 이내)
    Status status = PENDING;              // PENDING → WITHDRAWN | ACKNOWLEDGED
    LocalDateTime requestedAt;
    LocalDateTime decidedAt;               // WITHDRAWN/ACKNOWLEDGED 전이 시각
    Long signatureEnvelopeId;              // WP-4 서명 봉투 연결(nullable, 선택적 — HC-13)
    @Version Long version;
}
```

`employerProposedDate`는 이 엔티티에 두지 않는다 — WP-3에서 별도 이력 엔티티로 분리한다(아래
§3-A, 3차 감사 정정).

**설계 변경(1차 정정)**:
1. **`REJECTED` 삭제, `WITHDRAWN`(직원 철회)으로 대체.** 사직은 근로자의 일방적 의사표시라
   사용자가 "거절"할 법적 권한이 없다(민법 §660). 상태 전이는 `PENDING → WITHDRAWN`(신청자
   본인만)와 `PENDING → ACKNOWLEDGED`(사장, §3-A 날짜 합의 완료 후)뿐이다.
2. **`ACKNOWLEDGED`는 `EmployeeStoreRelation.changeActive(false)`를 호출하지 않는다.** 실제
   비활성화는 WP-2의 기존 토글이 담당 — 사장이 실제 마지막 근무일에 맞춰 별도로 누른다.

`ACKNOWLEDGED`는 계약을 종료시키는 행위가 아니라 접수 확인이지만, "근로계약 종료 의사표시를
수리한다"는 실질 자체가 `CONTRACT_MANAGE`에 가깝다는 1차 감사 지적을 존중해 **`ACKNOWLEDGED`
전이는 사장 전용**으로 둔다(민법 §660이 근거이지, 이 코드베이스가 계약서 서명을 `CONTRACT_MANAGE`로
감싸는 기존 관례는 보조 근거일 뿐 — §4에서 이 구분을 더 명확히 한다).

- Flyway: `V93__create_employee_resignation_request.sql` 신설 — `desiredResignationDate`·
  `agreedResignationDate`·`signatureEnvelopeId` 전부 이 파일 하나에 포함(착수 시점에 최신 V
  번호 재확인)
- 제출 시 검증: 신청자 본인의 `relation`인지(BOLA), `relation.isActive`가 이미 false면 거부
- **정합성 노트**: 사장이 WP-2 토글로 먼저 비활성화하면, 목록 조회는 `relation.isActive=true`인
  것만 "처리 대상"으로 필터링해 자연스럽게 액션 목록에서 빠지게 한다
- **알림**: `AttendanceCorrectionService` 패턴을 따라 afterCommit에서 발행
- **PII**: `reason`은 자유서술 — 응답 노출은 신청자 본인·해당 매장 사장으로 한정, 로그 마스킹

## 3-A. WP-3 — 퇴사일 조율(negotiation) 방식 (3차 감사로 재설계)

**정정 배경**: 1차안은 `employerProposedDate` 필드를 매번 덮어써 "누가 언제 어떤 날짜를 냈는가"가
사라지는 모델이었다. 이 코드베이스는 옆 도메인(`StoreDelegationAudit`·`ElectronicSignatureAccessAudit`·
`ElectronicSignatureAttempt`)에서 이런 종류의 의사결정 이력을 전부 append-only로 남긴다 — 왕복
협의만 예외로 둘 이유가 없다. 분쟁("내가 먼저 이 날짜를 냈는데 무시당했다")이 생기면 이력이 곧
증거다.

### 신규 엔티티: `EmployeeResignationDateProposal`

```java
@Entity
public class EmployeeResignationDateProposal {
    Long id;
    EmployeeResignationRequest request;   // 어느 신청에 대한 제안인지
    ProposerRole proposerRole;             // EMPLOYEE | MASTER
    LocalDate proposedDate;
    LocalDateTime proposedAt;
    boolean accepted;                      // 상대가 이 제안에 동의했는지
}
```

- append-only — 수정·삭제 없음. `request.agreedResignationDate`는 **마지막으로 `accepted=true`가
  된 제안의 `proposedDate`를 복사한 캐시 필드**(조회 편의용, source of truth는 이력 테이블)
- Flyway: `V94__create_employee_resignation_date_proposal.sql`(V93 이후 신규 파일 — WP-1의
  엔티티와 파일을 나눠 각 WP가 독립적으로 마이그레이션 소유권을 갖게 한다)

### 상태 전이

```
[직원] 최초 제출 — proposal(EMPLOYEE, desiredResignationDate) 1건 생성
   │
   ▼
[사장] 응답
   ├─ 동의 → 해당 proposal.accepted=true, request.agreedResignationDate 갱신
   └─ 역제안 → proposal(MASTER, 새 날짜) 신규 생성(기존 proposal은 그대로 accepted=false로 남음), 알림 발송
                │
                ▼
        [직원] 응답 — 동의 또는 재역제안(반복, 왕복 횟수 제한 없음)
   │
   ▼
agreedResignationDate 확정 → WP-4(전자서명) 개시 가능
```

- **경과일 표시(신설)**: 왕복 횟수를 제한하지 않는 대신, `PENDING` 상태로 며칠째인지를 목록
  화면에 표시한다(민법 §660 — 통고 후 1개월 경과 시 자동 효력 발생 — 와 앱 상태가 무한정
  괴리되지 않도록 시각적 신호만 준다. 자동 만료·강제 확정 로직은 넣지 않는다 — 그건 다시 법적
  판단이 필요한 영역이다)
- 사장 쪽 응답도 `assertMasterOwnsStore`만 사용(매니저 위임 없음)

| GET | `/resignation-requests/{id}/proposals` | 당사자(신청자 또는 사장) | 제안 이력 전체 조회 |

- **하드 제약(HC-8)**: `EmployeeResignationDateProposal.proposedDate`·`agreedResignationDate`
  전부 급여·보존기간 로직 미연결(HC-1과 동일 원칙)
- **하드 제약(HC-12, 신설)**: `agreedResignationDate`가 null인 상태에서는 WP-4의 서명 개시
  API가 400을 반환한다 — 이 가드는 **WP-4가 구현**한다(WP-3은 필드만 제공, 가드 소유권은
  서명을 개시하는 쪽에 있는 게 맞다 — 1차 설계가 이 소유권을 반대로 뒀던 걸 정정)

## 4. WP-4 — 근로자·사용자 양측 전자서명 (3차 감사로 재설계)

### 기존 인프라 조사 결과 — 재사용 가능하지만 "자동 상속"은 아니다

- `ElectronicSignatureEnvelope`/`Party`(`domain/`) — `SignatureSubjectType`+`subjectId`로 스코프되는
  범용 다자 서명 엔진. `storeId` 필드가 있어 매장 단위 인가와 잘 맞물린다(스코프 자체엔 함정 없음).
  `RESIGNATION_ACKNOWLEDGMENT` 값 하나만 `SignatureSubjectType`에 추가하면 봉투·파티·순차서명·
  PDF 해시 무결성은 그대로 재사용된다.
- **정정 — 보존정책은 자동 상속이 아니다.** `ElectronicSignatureRetentionPolicies.java`는
  subjectType별 **전용 `@Component` 서브클래스 3개**(`ManagerDelegationSignatureRetentionPolicy`
  5년·`LaborContractSignatureRetentionPolicy` 3년·`EmploymentAmendmentSignatureRetentionPolicy`
  3년)로 구현돼 있고, **`GUARDIAN_CONSENT`는 아예 정책이 없다**(선례가 이미 이 문제를 갖고 있다).
  `RESIGNATION_ACKNOWLEDGMENT`를 그냥 추가만 하면 **파기 정책 없는 서명 증적**이 생겨 개인정보
  파기의무 위반 소지가 된다. → **`ResignationAcknowledgmentSignatureRetentionPolicy` 신규
  컴포넌트를 반드시 함께 추가한다**(보존기간 값은 `LaborContract`류와 같은 3년을 잠정 채택 —
  G-6이 "기산일 로직"을 다루는 것과 달리 이건 "기존 정책 패턴을 새 문서 유형에 반복 적용"이라
  결이 다르지만, 정확한 보존연한은 노무 자문이 필요할 수 있어 **잠정값임을 코드 주석에 명시**)
- **정정 — 봉투/파티 생성은 subject 전용 메서드로만 가능하다.** `ElectronicSignatureApplicationService`가
  `createLaborContract()`류 subject별 전용 메서드를 갖는 구조다 — 여기에 `createResignationAcknowledgment()`류
  메서드를 신설해야 한다(targets에 추가, 3차 정정).
- **정정 — VERIFIED 후처리 위치.** 서명 완료 후속 처리(`ElectronicSignatureWorker`의 subject별
  if/else 분기)에도 `RESIGNATION_ACKNOWLEDGMENT` 분기를 추가해야 한다(targets에 추가, 3차 정정).
- FE `ElectronicSignScreen.tsx`는 subject 무관 범용 화면이라 `subjectLabel()` 매핑 한 줄만
  추가하면 된다 — 이 부분은 1차안 그대로 유효하다.

### ⚠️ 핵심 정정 — 전자서명은 기본 비활성 상태다, 확인의 전제조건으로 강제할 수 없다

`application.yml:353` — `sodam.integration.electronic-signature.mode`가 기본값 **`off`**다.
`off` 상태에서는 `MockElectronicSignatureGateway`도 `LiveBarocertElectronicSignatureGateway`도
빈으로 등록되지 않고, `ElectronicSignatureCoreConfiguration`이 `@ConditionalOnBean`으로 막혀
**서명 코어 서비스 자체가 존재하지 않는다.** dev 프로필만 `mode: mock`으로 재정의돼 있다
(`application-dev.yml:112`) — **운영 환경은 사람이 `SODAM_INTEGRATION_ELECTRONIC_SIGNATURE_MODE=live`를
명시적으로 켜야만 서명이 동작한다**(Toss 실키·LLM 실키와 같은 H-계열 활성화 패턴).

**1차·2차안은 "서명 완료가 확인(acknowledge)의 전제조건"으로 설계했는데, 이대로면 운영 환경에서
사람이 이 통합을 켜기 전까지 사직 확인 자체가 영구히 불가능해진다.** 이 프로젝트의 다른 모든
유료 통합(`NoopReceiptOcrClient`·`TemplateLaborRiskNarrator`)은 비활성 상태에서도 핵심 기능이
100% 동작하고 유료 기능은 "있으면 더 좋은" 계층으로 얹힌다 — 이번에도 같은 원칙을 따른다
(HC-13, 신설).

**정정된 설계**:
1. `agreedResignationDate` 확정 시 사장이 "서명 요청" 트리거(사장 전용, HC-9)
2. **전자서명 통합이 `off`(코어 서비스 빈 부재)면**: 서명 요청 액션 자체를 UI에서 숨기거나
   "전자서명이 아직 활성화되지 않았어요 — 서면으로 확인해 주세요" 안내로 대체하고, `acknowledge()`는
   서명과 무관하게 **그대로 동작**한다(원래 §3 설계 그대로 — 서명은 선택적 강화 계층일 뿐)
3. **전자서명 통합이 활성(`mock`/`live`)이면**: 서명 요청 → 직원·사장 순차 서명 → 완료
   (`VERIFIED`) 시 `EmployeeResignationRequest.signatureEnvelopeId` 연결. 이 경우에도
   `acknowledge()`가 서명 완료를 **기다리지 않는다** — 사장은 서명 여부와 무관하게 확인을
   진행할 수 있고, 서명은 병행되는 별도 증적 절차로 취급한다(운영 판단에 따라 "서명 완료 전엔
   확인 버튼 비활성화" 같은 UX 강제를 나중에 추가할 수는 있지만, **코드 레벨 하드 블로킹은
   이번 범위에 넣지 않는다** — HC-13)
4. **서명 문서 내용(L-3/C-6 대상, §4-A)**: "○○님과 △△매장은 [합의된 마지막 근무일]을 기준으로
   근로관계를 종료하기로 확인합니다" + 근로기준법 §36 인용 안내 + **"이 확인은 정산 금액·지급
   시기를 확정하지 않습니다"라는 명시적 면책 문구**(3차 정정 — 날짜를 서명으로 못박는 행위조차
   G-15의 미확정 영역과 완전히 분리되지 않는다는 지적을 받아, 분리를 코드 설계가 아니라 **문서
   문구로도** 명시). 최종 정산 금액·급여 확정 문구는 절대 포함하지 않는다(HC-10)
5. 서명 완료 후에도 `EmployeeStoreRelation.changeActive(false)`는 호출하지 않는다(HC-2 유지)

### 4-A. 신규 게이트 [[C-6]] — 퇴사 확인서 서명 문구 확정 대기

위 4번의 문서 문구는 **가안(假案)이다.** `docs/RELEASE_GATES.md`의 [[L-3]](노무 문구·근로계약서
법적 검토 미완료)가 이미 이 범주를 포괄하고 있어 새 L-ID는 만들지 않되, "문구 없이는 노출 금지"
성격의 C-계열로 진행 상황을 추적한다 — 근거는 이 프로젝트가 이미 **동의 화면 문구 하나**(C-1)에도
게이트를 걸었고, **서명 직전 노출되는 문구**(G-20, 근로계약서 조항 설명)에는 노무사 게이트까지
신설한 선례가 있다는 점이다. 서명 대상 문서 본문은 그보다 결코 가볍게 다룰 수 없다. §7에 반영,
`docs/RELEASE_GATES.md`에도 별도로 등록한다(이 문서와 동기화 유지).

## 5. WP-5 — 화면 설계 (v3 디자인 시스템 "링&패스" 기준, 3차 감사로 상호작용 정정)

### 시각 언어는 재사용, 상호작용은 다시 설계

이번 세션에서 구현한 "제안 카드" 시각 언어(`AppCard variant="plain"`, `AppButton` outline/secondary/
ghost)는 그대로 재사용하되, **"적용/닫기" 2액션은 그대로 옮기지 않는다.** AI 제안의 "닫기"는
무해한 폐기지만, **사람이 실제로 보낸 날짜 역제안**을 "닫기"로 처리하면 상대에게 아무 신호도
가지 않는 무응답이 되고, 이게 "사장이 무시했다"는 실제 갈등으로 번질 수 있다(3차 감사 지적).

**정정된 상호작용**:
- 액션 2개: **"이 날짜에 동의"** / **"다른 날짜 제안하기"** — "닫기"에 해당하는 액션 없음
- 카드에 **제안자(직원/사장)와 제안 시각**을 명시(누가 언제 낸 제안인지 항상 보임)
- "나중에 결정"에 해당하는 행동은 카드를 목록에서 사라지게 하지 않는다 — 협의 중 상태는 계속
  목록에 남아 언제든 다시 응답할 수 있다
